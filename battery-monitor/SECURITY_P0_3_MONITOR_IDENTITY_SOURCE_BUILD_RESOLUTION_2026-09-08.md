## Finding resolved at source/build level

P0-3 originally allowed a hostile LAN host to spoof UDP discovery, claim an existing `BM-XXXXXX` Device ID, redirect Windows to another address, or feed a false battery state through unauthenticated status responses.

The source/build resolution no longer treats the public Device ID, mDNS metadata, legacy discovery JSON, or plain HTTP reachability as proof of identity.

## Monitoring Identity Key

Each physical monitor now has a separate persistent **Monitoring Identity Key**:

- 256 random bits generated on the ESP32;
- stored in its own NVS namespace as security material;
- independent of the user-facing Device Password;
- not derivable from Device ID/MAC address;
- stable across normal Device Password rotation;
- stable across ordinary application-only firmware updates;
- destroyed when the destructive factory/recovery merged image resets NVS.

Malformed existing Monitoring Identity Key state fails closed rather than silently rotating identity.

The Monitoring Identity Key authorizes monitor identity/status verification only. It does not replace the Device Password as normal administrative authority.

## Pairing / trust acquisition

### Authenticated LAN pairing

For an online unpaired monitor, Windows:

1. starts from an untrusted discovery candidate;
2. authenticates with the existing P0-2 Device Password challenge/HMAC flow;
3. requests `POST /api/monitor-key` using the authenticated management session + CSRF token;
4. derives a session-specific wrapping key from the P0-2 management key using:

   `BATMON-MONITOR-KEY-WRAP-V1|<session>|<csrf>`

5. authenticates/decrypts the 32-byte Monitoring Identity Key from AES-256-GCM;
6. binds the GCM envelope with AAD:

   `BATMON-MONITOR-KEY-AAD-V1|<deviceId>|<session>`

7. stores the recovered Monitoring Identity Key using Windows DPAPI.

The Monitoring Identity Key is never returned by an unauthenticated LAN endpoint.

### Trusted USB pairing

Trusted physical USB may pair a Windows account without knowing the Device Password:

- serial command: `BATMON1 MONITORKEY`;
- firmware returns the 32-byte key only on the trusted physical serial path;
- Windows deliberately redacts the response from the visible log;
- the clear key exists in memory only long enough to save it with DPAPI, then buffers are zeroed where practical.

## Authenticated discovery v2

Windows sends a fresh 128-bit client nonce:

`BATMON_DISCOVER_V2 <32-hex-nonce>`

The ESP32 returns an envelope containing:

- protocol `BATMON_DISCOVERY_V2`;
- the request nonce;
- Base64 of the exact UTF-8 discovery payload bytes;
- HMAC-SHA-256 over the exact payload bytes with domain separation.

The authenticated message framing is:

`HMAC-SHA256(MonitoringIdentityKey, UTF8("BATMON-DISCOVERY-V2|" + nonce + "|") || payloadBytes)`

The signed payload includes Device ID, name, hostname, current IPv4 address, port, API version, and firmware version.

### Address binding / redirect defense

For a trusted response Windows requires all of the following:

- a recent nonce generated by that Windows discovery attempt;
- valid HMAC under the locally stored Monitoring Identity Key for the claimed Device ID;
- valid IPv4 port/address shape;
- the **signed IP inside the authenticated payload must equal the actual UDP source IP**.

The accepted current network address is the UDP source endpoint. A captured valid response replayed from another host therefore cannot move an already-trusted Device ID to the attacker's address.

Legacy `BATMON_DISCOVERY_V1` remains only for visibility/backward compatibility. It can create an **unpaired candidate**, but it is never cryptographic identity and cannot move a device for which this PC already has a trust key.

## Authenticated battery status

Paired Windows clients no longer accept ordinary `/api/status` as authoritative battery state.

For every poll:

1. Windows generates a fresh 128-bit nonce;
2. requests `GET /api/status-auth?nonce=<nonce>`;
3. firmware returns protocol `BATMON_STATUS_V1`, the nonce, Base64 exact status payload bytes, and HMAC;
4. Windows verifies protocol, nonce, HMAC and expected Device ID before applying voltage/state/threshold metadata.

HMAC framing:

`HMAC-SHA256(MonitoringIdentityKey, UTF8("BATMON-STATUS-V1|" + nonce + "|") || payloadBytes)`

An old valid status response cannot answer a fresh poll because the nonce changes. Modification of voltage, state, threshold, name, RSSI, or other signed payload fields breaks authentication.

## Windows trust behavior

Windows now distinguishes:

- **Unpaired candidate** — visible but no Monitoring Identity Key exists locally; no battery reading is trusted;
- **Trusted** — a local DPAPI-protected key exists and authenticated discovery/status verifies;
- **Identity failure** — a known/trusted identity produces a failed cryptographic proof; reported battery voltage/state is discarded and Windows surfaces an identity-specific warning rather than treating it as ordinary offline behavior.

Additional behavior:

- HTTP automatic redirects are disabled for Battery Monitor device traffic;
- status Device ID must match the expected monitor;
- authenticated discovery controls address changes, including DHCP changes;
- a remembered DPAPI Device Password may be used once to auto-pair an existing saved monitor after upgrade;
- otherwise the user can pair once with Device Password or trusted USB;
- Device Password rotation does not invalidate the Monitoring Identity Key;
- removing a device from the PC removes both remembered Device Password and DPAPI-protected Monitoring Identity Key.

## Wi-Fi recovery behavior corrected while closing P0-3

A configured monitor with saved home Wi-Fi no longer automatically exposes provisioning merely because the router/network is unavailable.

- it continues retrying the saved infrastructure network;
- secure provisioning requires the approved 5-second BOOT physical-presence action when the old LAN is unreachable;
- an online/reachable monitor can still enter Security-2 setup through authenticated Change Wi-Fi;
- intentional first setup / explicitly absent Wi-Fi can enter the protected Security-2 provisioning flow as designed.

This avoids turning an infrastructure outage into an automatic provisioning-state transition.

## Deterministic protocol validation

The Windows client has an explicit `--protocol-self-test` mode executed by CI before publish.

The self-test validates production helpers using fixed independent vectors for:

1. discovery HMAC exact-byte framing/domain separation;
2. monitoring-key wrap-key derivation;
3. AES-256-GCM monitoring-key decryption with fixed IV, ciphertext, tag and AAD.

The final validated run #107 passed this step before producing the Windows bundle.

## Factory/update persistence check

The generated CI merged firmware image was inspected in addition to ordinary compile validation:

- merged image size: 4 MiB;
- default NVS region `0x9000-0xDFFF` is blank (`0xFF`) in the merged image;
- Factory Flash / Recovery writes the merged image starting at `0x0`, so the destructive path replaces NVS and therefore destroys the prior Monitoring Identity Key;
- normal Update Firmware writes only the application image at `0x10000`, leaving NVS and Monitoring Identity Key intact.

This matches the intended identity semantics. Physical hardware testing must still prove the behavior end-to-end.

## What this resolution does not claim

P0-3 is **not field-closed** yet.

Source/build validation proves the implementation compiles, packages, and passes deterministic host-side protocol tests. It does not replace real-hardware and hostile-LAN testing.

Still required on physical hardware:

- trusted monitor survives DHCP address changes while remaining authenticated;
- rogue responder cannot move a trusted Device ID to another address;
- rogue responder cannot forge discovery for a trusted Device ID;
- rogue HTTP responder cannot feed a voltage/state that Windows accepts;
- replayed discovery/status messages fail against fresh nonces;
- redirects are not followed;
- LAN and USB pairing both work end-to-end;
- password rotation preserves monitoring trust;
- destructive factory identity reset breaks old Windows trust;
- DPAPI trust persists across Windows restart and is removed when explicitly forgotten/removed;
- 5-second BOOT Wi-Fi recovery and authenticated Change Wi-Fi both work physically.

## Remaining security boundaries

P0-3 authenticates integrity/identity of discovery and status; it does not encrypt non-secret LAN metadata/status.

Separate unresolved security work remains:

- physical flash/NVS extraction: NVS Encryption / Flash Encryption;
- device-side firmware authenticity: Secure Boot and production ROM-download policy;
- Arduino-ESP32 3.3.11 WebServer slow-header availability issue: update to a fixed core or incorporate the upstream fix before hostile-LAN deployment;
- firmware release signing enforcement, Windows code signing, Android release signing, and CI supply-chain hardening;
- evaluate authenticated TLS/device certificates if transport confidentiality or stronger general LAN transport identity becomes a product requirement.

Do not burn Secure Boot eFuses on development boards until the separate production checkpoint is completed.
